## 1. ЧТО ЭТО ЗА ПРИЛОЖЕНИЕ

Клиент-серверное SPA для персонального планирования питания. Курсовой проект.

**Возможности:** генерация планов питания (AI + каталог 774 блюда), учёт
аллергий и пищевых ограничений, «холодильник» (личные продукты с фото),
распознавание еды по фото, AI-чат, анализ тела по фото, статистика и экспорт,
планы тренировок, подписка Stripe, админ-панель модерации.

### Стек

|---|---|
| Backend | NestJS 11, TypeScript, Node.js 22 |
| БД | PostgreSQL 16, Sequelize 6 + sequelize-typescript |

| Прочее | Stripe 23, multer, sharp, nodemailer, winston, `@nestjs/throttler`, `@nestjs/cache-manager` |

## 2. ЗАПУСК И ДОСТУП

**Важно про твои возможности.** Ты не исполняешь команды на машине
пользователя и не можешь сам запустить Docker, поднять БД или открыть
браузер. Поэтому:

- если пользователь дал живой адрес приложения — тестируй по нему
  (запросы к API можно делать напрямую);
- если доступа нет — **тестируй по коду** и помечай каждый вывод `[ПО КОДУ]`;
- если для проверки нужно запустить что-то на его машине — **попроси его
  об этом и дождись ответа**, а не описывай действия в прошедшем времени.

Никогда не пиши «я запустил», «я проверил в браузере», если ты этого
фактически не делал.

```bash
./rebuild.sh all      # собрать и поднять всё (postgres + api + web)
./rebuild.sh web      # только фронтенд
./rebuild.sh api      # только backend

# Адреса:
https://localhost          # приложение через nginx (самоподписанный TLS)
http://localhost:3000/api  # API напрямую
```

Проверки, которые пользователь может выполнить по твоей просьбе:

```bash
npm run build                # сборка backend
npm test                     # 574 unit-теста
cd frontend && npm run build # сборка frontend
```

## 3. ЧТО ПРОВЕРЯТЬ

### 3.1. Функциональная логика (приоритет)

Для каждого сценария проверь **не только «работает/не работает», но и
правильность результата**.

**Генерация плана питания** — ядро проекта
(`src/meal-plan/meal-plan.service.ts`, 3016 строк):
- Учитываются ли аллергии пользователя? Может ли блюдо-аллерген попасть в план?
- Соблюдаются ли пищевые ограничения (веганство, диета)?
- Суммируется ли калорийность/БЖУ к заданной цели? Насколько расходится?
- Нет ли бесконечных циклов при нехватке подходящих блюд?
- Детерминирован ли результат при одинаковом входе?

**Расчёты** — пересчитай вручную и сравни с тем, что показывает приложение:
- БЖУ блюда на порцию и на приём, единицы (г/мл/шт);
- BMR/TDEE/ИМТ в анализе тела;
- Итоги суток и недели в статистике.

**Холодильник:** пересчёт единиц измерения, связь с планом питания,
загрузка фото.

**Распознавание еды:** что происходит при низкой уверенности модели,
обрабатываются ли нераспознанные позиции, нет ли ложных предупреждений
об аллергенах.

**Подписка:** корректно ли ограничивается платный функционал, что видит
пользователь без подписки, нет ли обхода.

**Авторизация и роли:** все ли защищённые страницы действительно требуют
входа; видит ли `guest` то, что не должен; доступен ли `/admin` только админу.

### 3.2. Визуал и UX

- Текст нигде не наезжает друг на друга и не обрезается.
- Кнопки одинаковой высоты, подписи читаются и по центру.
- Ничего не выходит за границы экрана, нет горизонтальной прокрутки.
- Состояния загрузки: видно ли, что идёт длительная операция (генерация плана,
  анализ фото) — или кнопка «замирает».
- Сообщения об ошибках: при любой неудаче пользователь должен понимать,
  что произошло. Отдельно проверь ошибки сети, 401, 402 (нет подписки), 500.
- Пустые состояния: что видно, если данных нет (нет планов, пустой холодильник).
- Контраст текста: читается ли он на своём фоне (особенно мелкий серый текст).

### 3.3. Целостность данных

- Сохраняются ли данные после перезагрузки страницы?
- Что происходит при частичном сбое (файл загружен, запись не создана)?
- Остаются ли «сироты» после удаления (план без дней, блюдо без ингредиентов)?
- Согласованы ли модели (`src/models/*.ts`), миграции
  (`database/migrations/*.sql`) и ручные `ensure-*-schema.ts`?

### 3.4. Граничные случаи

Проверь намеренно некорректные данные: пустые поля, отрицательные числа,
огромные значения, текст вместо числа, дата в прошлом, очень длинная строка.
Приложение должно отвечать понятной ошибкой, а **не** падать с 500 и не
сохранять мусор.

Твой ответ — готовый документ, не рассуждения.

### Сводка

Сколько проверено сценариев, сколько дефектов, распределение по
критичности, общая оценка готовности к защите (кратко, до 200 слов).

### Реестр дефектов

Таблица по критичности:

| ID | Критичность | Область | Где | Что не так | Как воспроизвести | Ожидаемое |
|---|---|---|---|---|---|---|

**Критичность:**
- **BLOCKER** — сломано или небезопасно, защиту с таким не пройти;
- **MAJOR** — неверная логика, потеря или порча данных;
- **MINOR** — заметно пользователю, но не критично;
- **NIT** — косметика.

Обязательно для каждого дефекта:
- **точные шаги воспроизведения** (что открыть, что нажать, что ввести);
- **что произошло** и **что должно было произойти**;
- если это вывод из кода, а не наблюдение — помечай `[ПО КОДУ]`;
- если не удалось проверить — помечай `[НЕ ПРОВЕРЕНО]` и напиши, что нужно
  для проверки.

### Что проверено и работает

Короткий список сценариев, которые прошли успешно — это тоже результат.

### Что осталось непроверенным

Чего ты не смог оценить без запущенного приложения, доступа к БД или

## 5. ПРАВИЛА

1. **Опирайся на реальный код репозитория.** Каждое утверждение — со ссылкой
   на файл и строку. Не выдумывай проблемы; если код корректен — не включай его.
2. **Различай факт и гипотезу.** Проверенное помечай явно, предположения —
   `[ПО КОДУ]` или `[ГИПОТЕЗА]` со способом проверки.
3. **Проверяй результат, а не только отсутствие ошибки.** Калории сошлись?
   Аллерген не попал? Цифры правдоподобны?
4. **Это курсовой проект**, а не продакшн с командой. Приоритет —
   корректность, безопасность и защищаемость решений, а не стиль кода.
5. **Не предлагай переписать проект** или сменить стек. Только конкретные дефекты.
6. Пиши **по-русски**; имена файлов, функций, маршрутов и команд — как в коде.
7. Отчёт — **финальный документ**. Не пересказывай процесс поиска.
